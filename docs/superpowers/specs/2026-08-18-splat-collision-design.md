# 3DGS コリジョン設計

splat シーンに衝突形状を与え、VelociDrone のドローンが床・壁・物で止まるようにする。

3DGS は向き付きブロブの雲で、三角形もコライダーも持たない。ゲーム側は素の Unity 物理
（`MeshCollider` 470 箇所、`Rigidbody` 173 箇所、`OnCollision*` あり）なので、Collider さえ
置けば機体の変形も衝突音もクラッシュ判定も既存コードが処理する。作るのは形状だけ。

床も含める。BlankCanvas には `TerrainCollider` があるが、splat の見た目の床はその上にあり、
コライダーが無いのですり抜けて下の地面まで落ちる（実機で確認、2026-08-18）。placement.json の
Y オフセットで splat を下げれば当たるが、それは床が平らな場合しか効かない回避策。

## 決定事項

| 項目 | 決定 | 根拠 |
|---|---|---|
| 生成 | **OpenVDB `vdb_tool`** のレベルセット経路 | 下の比較表 |
| 手順 | `points2ls` → `median` → `open` → `ls2mesh` → **簡略化** | 細かく焼いて後で減らすと、隙間が 2〜5 倍良くなる |
| voxel | **覆いを保てる最細**（シーンごと） | 隙間は voxel に比例、三角形は簡略化で切り離せる |
| radius | 2.0 voxel | 1.5 未満は焼けずに空メッシュになる |
| 平滑化 | **`median iter=1`**（`gauss` ではない） | ガウシアンはエッジを保存しない |
| 整形 | **`open radius=1`**（`close` ではない） | 閉じると凹みが埋まり、柱の根元が漏斗になる |
| メッシュ化 | `ls2mesh adapt=0.9` | 平坦面だけ間引く |
| 簡略化 | **`fast_simplification` で 500K 三角形へ** | 二次誤差最小化。隙間を悪化させない |
| 三角形の予算 | 1 シーン 500K **三角形** | Office が 351,633 積んでいる。その 1.4 倍 |
| レイヤー | `Default`(0) | Office の 598 collider が全部 Default |
| MeshCollider | convex=false, cookingOptions=30, material なし | Office と同一設定 |
| 座標変換 | **Y 反転 + 巻き順反転** | メッシュはソース ply の座標系で出る |
| 配置 | splat ルートの子 GameObject | placement.json の transform がそのまま乗る |

## 手法の比較（実測、drjohnson）

「隙間」はメッシュ頂点から最も近い splat 中心までの距離。コリジョン面が実際の面から
どれだけ浮いているかで、**ドローンが床から何 cm 浮くか**そのもの。

```
                                    隙間(中央値)   p90     最大      tris     角     柱の根元
splat-transform    voxel 0.12         0.267      0.628   13.45   116,513  キューブ   -
OpenVDB gauss+close voxel 0.12        0.247      0.363    0.50    40,736  丸い      漏斗
OpenVDB gauss+close voxel 0.04        0.083      0.122    0.17   359,308  丸い      漏斗
OpenVDB median+open voxel 0.04        0.065      0.090    0.13   509,662  鋭い      正常
OpenVDB median+open 0.02 → 500K       0.032      0.046    0.06   500,000  鋭い      正常
```

**現状比で隙間が 8.3 倍。** `max 13.45` は splat-transform 側の実態で、**13 m 離れた場所に
コリジョン面がある**。最終行の 0.06 と比べると 224 倍。

### 細かく焼いて後で減らす手順

これが効いた理由は単純な非対称性にある。**隙間は voxel に比例し、三角形は voxel の 2 乗で
反比例する。** だから細かく焼いて三角形だけ落とせば、隙間は細かい voxel のもの、三角形数は
粗い voxel のものになる。

二次誤差辺収縮（quadric edge collapse）は元の面への二乗距離を最小化する。**それは隙間が
測っている量そのもの**なので、簡略化しても面が離れない。実測では**わずかに近づいた**
（drjohnson voxel 0.02 の理論隙間 0.041 に対し、簡略化後 0.032）。

```
                voxel   焼いた直後の tris   500K に簡略化後の隙間   250K 後の隙間
drjohnson       0.020        2,069,108           0.032              0.033
playroom        0.008        2,963,052           0.012              0.023 *
textilni        0.060        4,043,532           0.110              0.113
```

\* playroom の 0.023 は voxel 0.015 からの 250K。0.008 からの 250K は未測定。

**隙間が簡略化後の三角形数からほぼ独立している。** 250K に落としても 500K とほぼ同じ。
つまり予算は品質を決めていない。決めているのは voxel だけ。

以前この spec は「メッシュ簡略化は密閉が壊れるので使わない」と書いていた。あれは外側フィルで
空間を封じていた頃の理屈で、物質を包む方式に変えた時点で前提が消えていた。**却下理由が
仮定のまま残っていた。**

床の階段状の凹凸も消える。二値占有では隣接セルの高低差の中央値が 0.120、つまり voxel
ちょうど 1 個ぶんの段差が床一面にあった（2 voxel 以上の段差が 45.5%）。レベルセットは
最初から連続なので、面が格子の間に落ちる。

### 三角形の数え方

`ls2mesh` は `adapt > 0` で同一平面のセルを統合するので、**三角形ではなく多角形を吐く**。
`element face N` は多角形の数。実測で **66〜71% が四角形**、残りが三角形で、扇形分割すると
**1.62〜1.74 倍**になる。Unity には三角形で渡すので、予算はこちらで数える。

この spec の初版はこれを取り違えていて、`drjohnson 0.03` を 375K で予算内と書いていた。
実際は **639K で超過**。

## パラメータの決まり方

**シーンに依存しない。** 体積が 3 倍違う 2 シーンで一致した：

```
              drjohnson (19x19x26m)   playroom (7.4x6.4x7.1m)
voxel 0.12         0.247                  0.243
voxel 0.06         0.124                  0.127
voxel 0.04         0.083                  0.086
voxel 0.03         0.062                  0.064
```

```
隙間 = 2.07 x voxel
```

`radius` は voxel 単位、`dilate` / `gauss` / `erode` も voxel 単位、`adapt` は無次元。
**決めるつまみは voxel ひとつだけ**で、他は自動で追従する。

### 上限は隙間、下限は速度（制約の両端）

**上限は隙間。** 隙間はドローンが面から浮く距離そのもので、機体サイズに対して評価する。

**下限はトンネリング。** `points2ls` は点を半径 `radius x voxel` の球として焼くので、1 枚の面
からできる壁の厚みは約 `2 x radius x voxel`、既定の `radius=2` なら `4 x voxel`。物理は 400 Hz
（`Fixed Timestep 0.0025`）なので、抜けない上限速度は `1600 x voxel` m/s：

```
voxel   壁の厚み   抜けない上限速度
0.008    0.032 m      46 km/h
0.02     0.080 m     115 km/h
0.03     0.12 m      173 km/h
0.06     0.24 m      346 km/h
0.15     0.60 m      864 km/h
```

これは splat-transform から乗り換えて**新しく背負った制約**。あちらの
`--voxel-external-fill` は外側を全部 solid にするので壁の厚みが実質無限だった。

### 噛み合っていた制約と、簡略化による破綻

三角形の予算が voxel を縛っていたあいだは、都合よく揃っていた。細かい voxel になるのは表面積
の小さい狭い室内で、そこはウープや 3 インチで遅く飛ぶ。速く飛ぶ広いフィールドは表面積が大きい
ので予算から voxel が粗くなり、壁が分厚くなる。**厚みが必要な場所に厚みが来ていた。**

簡略化を入れて予算が voxel を縛らなくなった結果、この保証が消えた。いまは点の密度が許すかぎり
細かくできるので、**狭い部屋ほど壁が薄くなる**。playroom の voxel 0.008 は壁 0.032 m で、
46 km/h までしか耐えない。

室内をウープで飛ぶなら足りる。だが**もう自動では安全にならない**ので、voxel を選ぶときに
想定速度を一緒に見る必要がある。ここは実機で確かめるべき箇所。

### 屋外に壁が無いこと

屋外フィールドで抜ける危険があるのは壁ではなく、**地面と単体の物**（建物・ポール・フェンス）。
地面は水平飛行では抜けようがなく、真下に突っ込む場合だけが問題になる。0.36 m の厚みは
518 km/h まで耐えるので、そこは効かない。

細い物はむしろ有利に働く。`points2ls` は点を半径 `2 x voxel` の球として焼くので、**実物より
太い塊になる**。voxel 0.09 ならフェンスの支柱が 0.36 m の柱として立つ。形は正確でないが、
抜けることはない。

そして**屋外では封じるものが何もない**。`--voxel-external-fill` を失ったコストは、屋内では
壁の厚みが有限になることだが、屋外ではゼロ。乗り換えの代償を払うのは屋内側だけで、そこは
遅く飛ぶ。

飛行範囲の外に出られることは残るが、それはコリジョンの精度ではなく設計の話で、キャプチャの
外はゲーム側の地形が受け持つ。

### voxel を決めるのは点の間隔

簡略化を入れたので、三角形の予算はもう voxel を縛らない。縛るのは**点群の密度**だけ。

`points2ls` は各点を半径 `2 x voxel` の球として焼く。voxel を細かくしすぎると球が隣の点に
届かず、面が数珠になって覆いが崩れる。限界はキャプチャごとに違う。

```
            覆いが保てる最細  崩壊した値   nn距離(p90)   限界/nn_p90
playroom        0.008          0.005        0.0087        0.92
drjohnson       0.020          0.015 (93%)  0.0162        1.23
textilni        0.060          0.045        0.0908        0.66
```

**限界は `nn_p90` とほぼ同じ**（比 0.66〜1.23）。ただし percentile では厳密に予測できない。
局所密度の問題で、大域統計に落ちない。drjohnson の nn_p90 は 0.0162 なのに 0.015 で覆いが
93% に落ち、playroom は nn_p90 0.0087 の下の 0.008 で完全に通る。

**規則：`nn_p90` から始めて、覆いが各軸 95% を割ったら粗くする。**

覆いの崩壊は**再現する**（drjohnson 0.010、playroom 0.005、textilni 0.030 と 0.045）。
このゲートには真陽性がある。前に作って捨てた 3 つのゲートと違う点はそこ。

### 到達点

```
            voxel   隙間     p90     tris     覆い   壁の厚み  耐える速度  想定機体
playroom    0.008  0.012   0.018   500,000  完全   0.032 m    46 km/h   ウープ
drjohnson   0.020  0.032   0.046   500,000  完全   0.080 m   115 km/h   3 インチ
textilni    0.060  0.110   0.140   500,000  完全   0.240 m   346 km/h   5 インチ
```

**隙間が機体幅に対して 0.13〜0.44 倍になった。** 直接生成のときは 0.5〜0.7 倍だった。

そして**トンネリングの余裕が減った**。壁の厚みは `4 x voxel` なので、細かくすると薄くなる。
playroom の 0.032 m は 46 km/h までしか耐えない。ウープの室内飛行なら足りるが、**ここは
もう自動では安全にならない**。voxel を細かくする判断に、速度の上限が付いてくる。

対処は 3 つ考えられる。`radius` を上げる（厚みは増えるが隙間も増える）、`-dilate` を後段で
足す（同じ）、あるいはシーンごとに想定速度から下限 voxel を決める。**未検証。**

## 浮遊ブロブの除去と最小特徴サイズ

実機で 3 シーン飛んだ結果（2026-08-19）：textilni は良好、drjohnson と playroom は
**小さな浮遊ブロブだらけ**。playroom は三角形が細かすぎて面のノイズになる。処理は
`tools/clean_mesh.py`。

### 島の残し方は「体積 OR 伸び」

キャプチャの floater をラスタライズすると、周囲に何も無い小さな閉じた塊になる。ゲームでは
**見えない壁**。連結成分として分離できるので機械的に落とせるが、**判定を片方だけにすると
必ず壊れる**：

- **体積だけ** — 手すり・パイプ・椅子の脚は長いが体積がほぼゼロなので消える
- **伸びだけ** — 広がったブロブが残る

**どちらか一方でも大きければ残す。** 両方小さいものだけがラスタライズのノイズ。体積は
`voxel^3` の個数で数える（無次元なので、シーンや voxel サイズが変わっても同じ数字が効く）。
既定は 100 voxel 体積、伸び 0.25 m。

### 簡略化の目標は辺の長さ（三角形数ではない）

細かい voxel で焼いて三角形数で削ると、密なところに**ドローンより小さい三角形**が残る。それは
ドローンが通れる場所を変えないので、情報を持たずに解像度だけ食う。

だから目標を**長さ**にする。辺長の中央値が最小特徴サイズに達するまで削る。三角形数は
押し付けるものではなく、シーンから出てくる。辺長は三角形数の平方根に反比例するので、探索
ではなく直接見積もりで 2〜3 回の反復で収束する。

## voxel の決め手は面の連結性

**この spec は voxel の選び方を二度間違えた。二度とも指標が嘘をついた。**

一度目は `nn_p90`（点群全体の最近傍距離）。playroom で 0.008 を選んだが、この統計は**密な床に
支配されていて、疎な壁を代表していない**。

二度目は「覆い（メッシュの extent が点群の extent を保つか）」。これは**面が粒々に崩れても
通る** — 粒が端から端まで散らばっていれば extent は満たすから。

正しい指標は**凝集度**、つまり最大連結成分が全表面積に占める割合。面が繋がっていれば 1 つの
成分が支配する。playroom で測ると：

```
voxel    成分数    面積        最大成分  島フィルタ後の面積
0.008   24,233   131.9 m2     77.0%    102.7 m2  (78%)
0.015    7,603   180.0 m2     80.0%    152.3 m2  (85%)
0.025    2,100   212.7 m2     86.3%    192.6 m2  (91%)
0.040      553   203.3 m2     90.9%    195.2 m2  (96%)
```

**細かいほうが面積が小さい。** 0.008 の 131.9 m2 は 0.025 の 212.7 m2 を下回る。面が形成されず、
孤立した球の粒々になっている証拠。`points2ls` の球が隣の点に届かなくなる限界を越えている。

そして 0.008 では**伸びで救われた成分が 0 個**。壁の断片が全部 0.25 m 未満に砕けていて、
OR 規則でも救えない。島フィルタが壁と天井を丸ごと食っていた。実機で「床と物しかない」と
見えたのはこれ。

**規則：島フィルタを通しても表面積が 95% 以上残る、最も細かい voxel。**

### 到達点（2026-08-19）

```
            voxel    tris     隙間    p90    面積保持   壁の高さ上端
playroom    0.040  136,724   0.072  0.092    96%       あり
drjohnson   0.050  277,736   0.089  0.114    95%       あり
textilni    0.060  499,998   0.112  0.141    99%       あり
```

**隙間は前の版より悪い**（playroom 0.015 → 0.072）。ただし前の版の 0.015 は「床と家具だけの
メッシュ」を測った値で、部屋が入っていなかった。**比較にならない数字を良い方向に読んでいた。**

splat-transform の 0.267 と比べれば 2.4〜3.7 倍で、そこは変わらない。

## 試して捨てた手（すべて実測）

**純収縮**（`erode` を `dilate` より多く）。隙間を詰める直接の手に見えるが、1 voxel 収縮で
隙間は 1.5 cm しか減らないのに頂点が 38% 消え、シーンの覆いが 19x19x26 から 14x18x16 に崩れる。
薄い構造から食われる。

**強い平滑化**（`gauss iter` を 2〜4 に）。レベルセットのガウシアンは面そのものを動かすので、
反復を増やすとシーンが 1/3 に縮む（19x19x26 → 6x6x15）。

**半径 1.5 未満**。球が voxel より小さいと焼けず、空メッシュが出る。エラーは出ない。

**自前の密度場 + マーチングキューブ**（`tools/gs_field_mesh.py`）。床の粗さは改善したが
（p90 3.3 倍）、等値面は「物質を包む」だけで**空間を封じない**ので部屋の形にならず、覆いも
足りなかった。OpenVDB は同じことをより良い実装でやる。**参照用に残すが本線ではない。**

**splat-transform の `--collision-mesh smooth`**。マーチングキューブでも二値の場では
sub-voxel にならない（0 と 1 の間の交点は必ず中点）。床の段差は 0.120 のまま動かなかった。

**`--voxel-carve`**。seed がシーンの飛行空間に入っていないと無反応（三角形数が 1 個も変わらない）。
seed を自動で決める手がないので採用しない。

## 前処理

```
<name>.ply
   │ align_ply.py --max-sigma 5        巨大ガウシアンを落とす
   │ splat-transform --filter-floaters --filter-cluster   浮遊物を落とす
   ▼
<name>-clean.ply  →  ply_points.py  →  points.ply（位置のみ）
```

`--max-sigma` は別セッションの実測による。utlida は最大のガウシアンがシーン全体の 180% の
大きさで、シーン中心から 148% の距離、つまりキャプチャの外側にある。**連結フィルタでは
落とせない** — それだけ広いものは定義上すべてと連結している。サイズで落とすしかない。

**注意：この前処理が OpenVDB 経路でも必要かは未検証。** `points2ls` は位置しか見ないので、
巨大ガウシアンも 1 個の点にしかならず、VDB は疎構造なので遠方の孤立点も安い。
splat-transform の voxel グリッドが破綻した理由（AABB が 414 倍に膨らむ）はここでは起きない。
**外して測ること。** いまの数字は全部「前処理あり」で取っている。

## オンディスク形式

`<game>/vdgs/<name>/collision.bin`。リトルエンディアン。

```
uint32   version      = 1
uint32   vertCount
uint32   indexCount
float32  verts[vertCount * 3]     // ソース ply の座標系のまま
uint32   indices[indexCount]      // 巻き順も生成そのまま（--reverse を付けたシーンだけ反転）
```

**ファイルは変換しない。** 変換済みディレクトリは ply の段階で `reprocess.sh` が処理済み、
`.ply` 直置きは `SplatCollision.Attach` が**実行時に** Y 反転と巻き順反転をする。ここで
変換すると二重になる。

`.ply` 直置きのシーンではファイル名が `<name>.collision.bin`。on/off と描画は
`placement.json` の `collision`（既定 true）と `collisionView`（既定 `"off"`）が持つ。
専用の設定ファイルは無い。

### 座標系

`vdb_tool` はソース ply の座標系のまま出す。キャプチャは `align_ply.py --mirror y`、つまり
`(x, -y, z)` で Unity に入るので、**メッシュも Y を反転する**。X は触らない。

### 巻き順は鏡映とは無関係に裏返っている（実測 2026-08-19）

**`ls2mesh` の出力はそれ自体が内向き。** 鏡映の副作用ではない。符号付き体積
（`Σ a·(b×c)/6`）を全 13 メッシュで測ると、OpenVDB 経由の 12 個が全部負：

```
playroom          136,724 tris   -24.51 m^3
drjohnson         277,736 tris  -107.97
textilni          499,998 tris -2571.04
luigi (旧経路)        113 tris    +8.77   <- splat-transform 由来だけが正
```

正が正しい。PhysX が非凸 MeshCollider の接触法線に使うのは `cross(b-a, c-a)` で、Unity の
カリングもこれと整合するから、座標系の左右手性は入ってこない。

**PhysX の三角形メッシュは片面。** 裏から来た剛体は止まらず、通り抜けて、向こう側で
逆向きに押さえられる。これは形状を変えずに巻き順だけ入れ替えた対照実験で出た（playroom、
半径 0.125 m の球、400 Hz）：

| 巻き順 | 落下開始 | 静止 | 起きたこと |
|---|---|---|---|
| 内向き | y=4.38 | y=2.349 | 屋根（2.789）を**突き抜け**、天井下面（2.380）に 31 mm 食い込んで静止 |
| 外向き | y=4.79 | y=2.944 | 屋根の**上**に載った（2.789 + 半径 0.125） |
| 外向き・室内から | y=2.15 | y=0.270 | **床**（0.152）に載った |

**「ときどきドローンが床の下に落ちる」の説明になっている。** 裏返った床は下向きに押す。

#### 判定基準にならない符号付き体積（実測 2026-08-19）

**一度これを自動判定に使い、間違えた。** 3 つとも負なのに、必要な処置が違う：

```
            体積        反転      落下テスト
playroom    -24.51     必要      反転で床（0.152）に着地。元だと天井裏に貼り付く
drjohnson  -107.97     必要      同じ
textilni  -2571.04    不要      反転すると 8/8 がメッシュの外へ抜ける
```

textilni は単純な閉じた立体ではない（非多様体エッジ 2,383）。また 3 つのうち**唯一
500K の間引き上限に当たった**メッシュでもある。level set か `fast_simplification` の
どちらかが別の規約を出しているが、**機構は分かっていない。** 分かっているのは、
落とした球がどちらで止まるかだけ。

だから `tools/glb_to_collision.py` の反転は **`--reverse` の明示指定**にした。既定は
生成そのまま。判定は必ず落下テストで：

```bash
/Applications/Unity/.../Unity -batchmode -quit -nographics \
  -projectPath unity/VDGSConverter -executeMethod CollisionTest.Run \
  -vdgsCollision build/splats/<name>          # ディレクトリでも <name>.ply でも通る
```

`mesh_to_glb.py` 側では反転しない — 2 箇所で反転すると打ち消し合う。

#### `.ply` 直置きでの PlyLoader による Y 鏡映（実測 2026-08-20、実機で発覚）

**コリジョンがずれる原因はここだった。** `PlyLoader.Load(path, out error, bool mirrorY = true)` —
`.ply` を実行時に読むとき、キャプチャが右手系 Y-down で Unity が左手系 Y-up なので、
**ロード時に Y を反転している**。変換済みディレクトリは `reprocess.sh` が変換前に処理して
いるので該当しない。コリジョンメッシュは ply から作るので、**反転前の座標**を持っている。

だから `playroom` と `drjohnson`（ディレクトリ）は合い、`textilni`（`.ply`）だけずれた。

補正は `SplatCollision.Attach` に置く — `dir` が `.ply` で終わるなら頂点の Y を反転し、
**同時に巻き順も反転する**（鏡映は行列式 -1 なので全部の面が裏返る）。オフラインのツール側
ではなく実行時に置くのは、**この反転が「ランタイムが ply をどう読むか」の性質**だから。
パイプライン側に置くと 2 つが別々に育つ — 実際にそうなって、気づくのに 1 回の飛行が要った。

**これは落下テストの珍現象も説明する。** 上下が逆の世界で球を落としていたので、地面の
「裏側」に着地していた。

#### gate として使えない落下テスト（実測 2026-08-20）

**実機で正しいと確認済みの drjohnson が落ちる。** playroom も落ちる。狙いの決め方を
4 回変えて、そのたびに結果が大きく動いた：

```
狙い方                        playroom      textilni
AABB 上空から                 屋根に着地     屋根に着地
Raycast で最深面              床 6/8        沈む
SphereCast で最深面           0/8           抜ける
支えのある最も低い開空間       2/8           -
```

原因は幾何ではなく**意味**。「どちら側が飛べる側か」はメッシュだけからは決まらない。
床の下の空洞も「支えのある開空間」なので、そこから落とせば当然抜ける。**点群を見ずに
これを判定する方法は無い。**

だから落下テストは**診断の道具**であって合否判定ではない。判定は実機で飛ぶ。

#### 層の重なり（意味に依存しない指標）

飛べる側が分からなくても、「垂直線が何枚の面を横切り、その間隔がいくつか」は測れる：

```
                  三角形   柱あたり面数   間隔中央値   0.25 m 未満
playroom  0.040    137K        6          0.245 m      50.9%
drjohnson 0.050    278K        6          0.326 m      42.9%
textilni  0.060    500K        8          0.352 m      29.9%
textilni  0.14     384K        8          0.787 m       8.1%
```

**この指標も合否には使えない** — 実機で正しい drjohnson が 42.9% で最悪の部類。部屋は
壁も家具も薄いので当然。**大きさの違うものを同じ物差しで並べない。**

voxel 0.14 の再焼きは 7 秒、間引き不要（384K < 500K 予算）。ステージングに
`textilni-v014.collision.bin` として置いてある。**飛んだ結果は不採用** —
柱の当たりが太い（壁厚 `4 x voxel` ≒ 56 cm。0.06 なら 24 cm）。屋外サイト向けの予備。

#### textilni は 0.06。穴は許容、0.14 は柱が太い

落下テストは通らない。voxel 0.060 / 500K 間引きの結果、狙った面から 2〜4 m 沈む
（交差回数の偶奇で確認、**6/6 が solid の内側で静止**）。あの柱には面が 12 枚、
0.17 m 間隔で積み重なっていて、0.25 m の球が入る隙間ではない。**薄いシートが
相互貫入している。** ブラウザ目視はこれを見逃した。

実機で 0.06 と 0.14 を同じトラックで飛ばした。0.14 は柱が太すぎる。0.06 は穴があるが
許容、柱の細さのほうが効く。**live は 0.06。** 落下テストが FAIL でも、飛ぶ側は通った。

#### 落下テスト設計での 3 度の失敗

1. **AABB の上から落とす** → 閉じた面なので**屋根の外側**に着地して PASS。床に一度も
   触っていない
2. **AABB の中心の柱を撃つ** → 64 × 80 m の site では中心が空中。「当たらない」で FAIL
3. **`Raycast` で面を探す** → 幅ゼロの線はサブセンチの薄片に当たる。球は乗れずに
   転がり落ち、「抜けた」と報告される。`SphereCast` に球の半径を渡すと解消

さらに `RaycastAll` / `SphereCast` は **1 コライダーにつき 1 ヒット**しか返さない
（三角形ごとではない）。層を降りるには直前のヒットの少し下から撃ち直す。

**「何かが止めた」を数えても巻き順は判別できない**（playroom は反転してもしなくても
6/8）。殻は深さによって両方向の面を持つので、床を抜けた球も床の裏で止まる。
測るべきは「**下向きに探して見つけた面の上で止まったか**」。

**1 軸反転（鏡映）を掛けるときは、そのぶんもう一度逆順にする。** 行列式 -1 で全部の面が
反転するため。playroom は鏡映なしで、それでも裏返っていた。

**`Physics.RaycastAll` は 1 コライダーにつき 1 ヒットしか返さない。** 三角形ごとではない。
だから「上から 1 回撃って部屋の中の床を探す」はできず、直前のヒットの少し下から撃ち直して
降りていく必要がある（`SplatCollisionProbe.InteriorDropPoint`）。1 回で足りると思って書くと、
屋根の上に球を置いて「コライダーは動いている」と報告する — 実際に一度そう報告した。

**splat-transform の出力とは変換が違う。** あちらは Z 軸 180 度回った座標で出るので X 反転が
要った。経緯は下の「二度間違えた記録」にある。混ぜないこと。

## ランタイム

新規 `src/VDGS/SplatCollision.cs`。責務は 3 つ。`collision.bin` を読む、`Mesh` を組む、
子 GameObject に `MeshCollider` を付ける。

```
VDGS_<name>                    <- placement.json の transform
  ├ SplatRenderer
  └ VDGS_<name>_collision      <- layer 0 (Default)
      └ MeshCollider  convex=false  cookingOptions=30
```

子にするのが要点で、位置・回転・スケールが親から自動で乗る。コリジョン側は座標を持たない。
in-game のスケール・高さ調整もそのまま追従する。`Mesh.indexFormat = UInt32` を明示する。

**スタッター対策。** スポーン直後の 1 フレームは既に数百 ms から数秒かかる（数十 MB の
`GraphicsBuffer.SetData`）。`Mesh` の生成はメインスレッドで行い、
`Physics.BakeMesh(mesh.GetInstanceID(), false)` をバックグラウンドスレッドで走らせてから
`MeshCollider.sharedMesh` に代入する。代入は焼き済みの結果を拾うだけなので安い。

**Web UI（実装済み）。** シーン行に `solid` チェックボックス。`POST /api/collision`
`{splat, on}` → `MeshCollider.enabled` の切り替えだけで再スポーン不要。飛びながら壁の有無を
切り替えられることが、そのまま検証の道具になる。

**off は「何も作らない」。** 最初はここを「spawn では必ず付けて enabled で切る」と書いて実装し、
**それは性能測定を静かに汚す**。`Physics.BakeMesh` が drjohnson の 27.8 万三角形を
`GraphicsBuffer.SetData` と同じフレームで焼くので、collision を切って測っても collision の
コストが載る。別セッションが「フォーマットのコストを測っていて、実は collision を測っていた」
という形で踏むところだった。

いまは `placement.collision` が false なら読み込まない（spawn report に
`collision off - mesh not loaded` が出る）。**飛行中に on にしたときに attach する**ので、
最初の 1 回だけ焼き代を払い、それ以降のトグルは無料。

**状態は `placement.json` の `collision`（既定 true）。** メッシュが焼かれているキャプチャは
固い部屋として飛ぶためのものなので、既定は on。このフィールドが無い既存ファイルは
`JsonUtility` が初期化子を残すので true のまま。

`hasCollision` と `collision` を status で**別々に返す**。`MeshCollider.enabled` は「切ってある」
と「メッシュが無い」の両方で false になるので、1 つにすると**ファイルの不在が誰かの設定に
見える**。同じ理由で `SavePlacement` は `collision` をメッシュがあるときだけ書き換える
（書き換えると、後でメッシュを焼いても off に固定される）。

## 検証

このプロジェクトで目視レビューは一度も欠陥を捕まえていない。ただし**自動判定は置かない。**

判定ゲートを 3 通り作って 3 回とも失敗した。AABB 比は外れ値 9 個で誤報を出し、パーセンタイル
基準は緩すぎて何も検出せず、`enclosed` は全ケースで 100% を返した（真陽性がゼロ）。
**再現しない現象に合わせて指標を調整し続けるのは、検証の形をした自己満足。**

代わりに**測れる量を出して人間が見る**。数字は 3 つ：

| 量 | 意味 | 良い値 |
|---|---|---|
| 隙間（頂点から最近傍 splat まで） | 面がどれだけ浮いているか | `2.07 x voxel` 付近 |
| 覆い（メッシュ AABB / 点群 AABB） | シーンが崩れていないか | 各軸 1.0 付近 |
| 三角形数 | 積載量 | < 500K |

`tools/preview.sh` がブラウザに splat とコリジョンを重ねて出し、この 3 つを画面に併記する。
**絵は判断のため、数字は絵が嘘をつかないため。**

## 二度間違えた記録

座標系の判定を二度誤った。**どちらも「正しく測った結果」に見えた。**

一度目は `.voxel.json` のヘッダを読んだ。`--filter-box` で軸ごとに片側だけ残して
`sceneBounds` の行き先を見る検定をして「X 反転なし、Y 反転あり」と結論した。
**ヘッダの座標系は `.collision.glb` 頂点の座標系と違う。** 検定は正しく動いていて、
測る対象が違った。

二度目はビューアーで luigi が逆さまに見えたことから「PlayCanvas のローダーが Y を反転して
いる」と推論した。実際にはローダーは何もしていない（ページ内でロード済みリソースの
`_centers` を読み出したらソース ply と完全一致、エンジンの gsplat シェーダーにも反転は無い）。
**luigi.ply がそもそも Y-UP だった**のを 3DGS 規約の Y-DOWN と思い込んでいた。
帽子とオーバーオールの色で y を測れば 30 秒で分かった。

決着させたのは AABB の残差比較。元の点群を 4 通りの符号で変換し、メッシュの AABB との
最大残差を出す：

```
Z rot 180  (-x, -y, z)   残差 0.12  ( 1.0 voxel)   <- 一致
Y flip     ( x, -y, z)   残差 1.06  ( 8.9 voxel)
X flip     (-x,  y, z)   残差 3.67  (30.5 voxel)
identity   ( x,  y, z)   残差 3.67  (30.5 voxel)
```

8.9 倍差がつくので曖昧さがない。**同じデータで IoU を取ると 0.203 対 0.193 で決着しない**
（playroom が X にほぼ対称なため）。向きの判定には IoU ではなく AABB 残差を使う。

もう 1 つ、再現しなかった観測を記録として残す。playroom を splat-transform の voxel 0.24 で
処理したとき、三角形が 254 個の破片に崩壊した（0.12 で 29K、0.32 で 864 と非単調）。
生成物は今も残っている。**同じコマンドで再現しない。** GPU の同時実行も直列と同じ結果を出した。
原因不明。voxel パイプラインを捨てたので追わないが、「一度起きた」ことは書いておく。

## やらないこと

- **SuGaR / 2DGS / GOF / PGSR。** 品質は最高だが学習時の画像とカメラが要る。手元にあるのは
  配布済みの `.ply` だけ
- **GS2Mesh。** 学習済みモデルから novel stereo view を作って既成のステレオマッチングで深度を
  取る。後処理として成立するが、学習時のカメラ姿勢が要る
- **Poisson 再構成。** 開口部に膜が張り、壁に穴が開く
- **凸分解 / 動的コリジョン / ナビメッシュ。** ドローンが止まればいい

## 実機で確定したこと

3. **床のコリジョンはドローンを止める。** playroom / drjohnson / textilni、いずれも確認。
4. **隙間の体感。** textilni は voxel 0.06（穴あり・許容）。0.14 は柱が太く不採用。
   playroom / drjohnson は 0.06 より細かい焼きで、飛んで問題なし。

まだ測っていないもの：

1. **`Physics.BakeMesh` の実測時間。** drjohnson 277,736 三角形
2. **`QuadColliders` がドローンであること。** 名前と衝突マトリクスからの強い推論。外れていても
   `Default` はほぼ全レイヤーと衝突するので実害は小さい

## WSL でのメッシュ化

`vdb_tool` は Windows 箱の WSL（Ubuntu 24.04）にある（`apt install python3-openvdb libopenvdb-tools`）。
**Mac では動かない。**

Homebrew の `openvdb` formula（13.0.0）は `-DOPENVDB_BUILD_VDB_TOOL=ON` を渡しておらず、
OpenVDB の CMake 既定は OFF。formula の test も `vdb_print` しか叩いていない。Mac で使うには
自前ビルドが要る。**やらない。** WSL に既に入っていて動いている。

分担はこうなる：

```
Mac   前処理（align_ply / splat-transform / ply_points）と後処理（座標変換）
WSL   vdb_tool のメッシュ化だけ
```

WSL に渡すのは位置だけの ply で、drjohnson で 38 MB、playroom で 23 MB。LAN 越しに
数秒。メッシュ化そのものが 10 秒なので、往復を含めても splat-transform 経路より速い。

**PowerShell を経由するとクォートが壊れる。** Mac bash → ssh → PowerShell → `wsl.exe` → bash の
4 段で、失敗は「本当の原因を名指ししない構文エラー」として出る。スクリプトを base64 で 1 個の
トークンとして渡し、bash 側でデコードする（`wslrun.sh` の形）。

## 再現コマンド

```bash
# 前処理（Mac）
python3 tools/align_ply.py in.ply clean0.ply --max-sigma 5
npx @playcanvas/splat-transform@3.3.0 -w clean0.ply --filter-floaters --filter-cluster clean.ply
python3 tools/ply_points.py clean.ply points.ply

# メッシュ化 + 簡略化（WSL、100〜400 MB の中間メッシュを転送しないため）
vdb_tool -read points.ply \
  -points2ls voxel=0.02 radius=2.0 width=4 \
  -median iter=1 -open radius=1 \
  -ls2mesh adapt=0.9 -write fine.ply
python3 tools/decimate_mesh.py fine.ply out.ply 500000     # fast_simplification

# 島の除去 + 簡略化の仕上げ、glb 化（Mac）
python3 tools/clean_mesh.py out.ply clean.ply --voxel 0.02 --min-voxels 100 --min-extent 0.25
python3 tools/mesh_to_glb.py clean.ply collision.glb

# ランタイム形式（Mac）。巻き順は既定では触らない。
# 落下テストが「要る」と言ったシーンにだけ --reverse を付ける（playroom と drjohnson は要る、
# textilni は付けると壊れる）
python3 tools/glb_to_collision.py collision.glb build/splats/<name>/collision.bin [--reverse]
```

WSL 側の用意（一度だけ）：

```bash
apt-get install -y python3-openvdb libopenvdb-tools python3-venv
python3 -m venv ~/vdgsvenv && ~/vdgsvenv/bin/pip install numpy fast-simplification
```

生成時間（drjohnson、10 コア）：voxel 0.02 で焼くのに 17 秒、500K への簡略化に 4 秒。
中間メッシュは 31 MB。textilni の voxel 0.03 は 409 MB / 106 秒まで膨らむので、
**簡略化は必ず WSL 側で走らせる。**
